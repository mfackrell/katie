# Chat-native projects

Katie can start a persistent software project from an explicit conversational request (including a same-chat “build that” referring to a saved user request). Ordinary questions and managed-agent/attachment conversations retain their existing paths. No agent dashboard is required. Project creation uses the durable chat request identity, validates the owning actor/chat and freezes the original user objective.

The scheduled mission dispatcher advances reviewed research, a structured specification, scoped approval, successive coding increments, preview delivery and a fresh whole-project assessment. Original objectives and user clarifications remain stored; each approved specification contains requirements, narrow allowed paths, phase-specific browser contracts, a complete final browser contract and finite ceilings. The last milestone must run the complete final contract. Phase success is never equivalent to whole-project success.

Coding requires an explicit connected target repository with the existing owner-only main-branch development workflow and private Preview deployment integration. Katie can ask for the repository in chat. The approved scope is presented concretely in that conversation, including all browser scenarios, allowed paths, source commit, deadline and budgets. One scope approval permits successive isolated draft jobs and bounded repairs within that scope. New services, credentials, dependency/deployment configuration, purchases, production publication and merging are not implicitly permitted. Targets must also be explicitly enabled in server-only PROJECT_PREVIEW_REPOSITORIES after their Preview environment is stripped of provider/GitHub/storage credentials and implicit cloud identity. Production and Development credential targets are preserved. Protected targets use an owner-configured production-only PROJECT_PREVIEW_BYPASS_SECRET and an anchored PROJECT_PREVIEW_HOST_PATTERN whose first capture is the exact nine-character deployment nonce. Mutable branch/project aliases are rejected; the matching-SHA deployment and status must both come from the Vercel GitHub app. Only Vercel’s edge receives that secret with manual redirect handling; the browser receives a short-lived HttpOnly cookie restricted to the exact deployment URL. Automatic system environment exposure is disabled for this target because Vercel otherwise exports an automation bypass into deployments. No bypass secret is injected into Preview builds, application requests, logs or model evidence. Deployment protection stays enabled. Missing integrations remain blockers rather than fabricated delivery. This release does not provision a new repository or service automatically and does not claim to have recreated Fortress America.

Each coding job starts from the previous immutable READY tested/reviewed commit on a new isolated branch. Server-owned project context is derived from the approved DB record and appended outside model prose. Ordinary inputs cannot inject a project marker. The native workflow preserves the original task and trusted browser tools before switching to the prior project commit. Independent tests, code review and bounded native repair remain unchanged. Actual built Next application checks run in a separate Linux user/network/PID namespace, with placeholder credentials and no route to production networks. Acceptance helpers fail closed without namespace support. Candidate CI and the application run inside separate bubblewrap filesystem/PID/user boundaries: preserved contracts, tools, reports and parent processes are not mounted; baseline dependencies are read-only. Install hooks are disabled and dependency manifests must match the previous verified commit. Before either publishing push, a trusted scope guard rejects the full cumulative staged diff outside approved paths, protected configuration, symlinks or submodules. The candidate cannot replace the preserved contract/tools. Project receipts require the exact approved scenario names/digest and matching test/review/browser/head SHA. Repaired runs require repaired browser evidence.

Parent projects require a successful same-head Preview deployment obtained from GitHub deployment/status records, never from a model-supplied URL. A separate bounded browser_check phase then executes the exact final contract against that actual deployed URL. Authentication/401 failures block for connection repair; failed gameplay permits bounded implementation repair. The private browser receipt binds the deployment ID, status ID, SHA, contract digest, URL and scenarios. No deployed browser pass means no completion. A new deployment after assessment requires a fresh deployed check and assessment. The same preserved browser engine runs both local and deployed checks. Each scenario has an independent browser context; navigation within a scenario retains localStorage for actual reload-persistence checks. The final independent mission assesses the entire original request against requirements and actual integrated evidence, and then returns the result to the original chat. Progress/final messages are persisted with stable IDs and chat polling only reads them; closing every browser does not stop the work.

Project limits are 8 native coding jobs, 12 milestone missions, 600,000 aggregate project-model tokens and 72 hours. New project phases have a 120,000-token ceiling within that unchanged aggregate limit, allowing conservative native web-search reservations plus independent review. Existing phases and ordinary mission defaults remain unchanged. Native GitHub coding model usage is additional, explicitly disclosed in the scope approval, and bounded separately by the existing job time/repair limits. This is not a dollar spending cap. All reservations, including uncertain calls and failed/superseded missions, remain charged. Parent and child mutations use the same advisory lock to prevent oversubscription and lock inversion. Current agent permission/capacity checks remain authoritative. Pause/stop invalidates leases; accepted external work may finish, but late results cannot advance a paused project. Resume preserves remaining budgets and refuses an expired or substantively blocked child rather than silently recreating its allowance. A malformed draft-blind assessment contract gets one durable retry with source-validator feedback; a second invalid contract remains blocked. Explicit resume can recover an eligible first failed contract from before this retry support, retaining the same job, attempt count, model calls, charges and deadlines.

Tables and RPCs are private, RLS enabled, SECURITY INVOKER with fixed search paths, and executable only by service_role. No browser receives a provider or database secret. Scope proposals are published in the same transaction as their digest. Digest-free approval requires the latest assistant proposal to carry the current full digest. Mid-project clarifications stop the superseded milestone and return to research/specification and fresh approval while preserving prior code and charges. Dispatch admission atomically checks parent scope/status/deadline and current assignment lease. Scope approvals are immutable digests; project controller outcomes and child creation are fenced and transactional. Message delivery is idempotent. Background controller failures block after three attempts.

## Validation

- projects-runtime: conservative natural intent, saved user-reference launch, request identity, scope-bound controls, cumulative two-stage coordinator, no completion without preview/final assessment, failed-browser rejection.
- projects-sql: real PostgreSQL project identity, actor/chat association, scope approval, child/lease fencing, pause/resume, immutable lineage, private privileges and concurrent aggregate reservation races.
- project-context / project-browser-check: strict marker/hash/parser bounds and real DOM interactions, deliberately wrong assertions, browser redirect confinement and server-side network isolation.
- autonomous-repair-handoff: actual workflow Bash, cumulative Git base, original trusted tools, missing/failed/wrong-head/partial/repaired browser receipt gates.
- Existing mission, managed-agent, chat, review, full CI build and smoke tests remain required.

Local runtimes without Linux user namespaces cannot execute the isolated acceptance integration. That is a failed local verification, not a reason to disable the boundary; complete CI runs it on the Linux runner. A live chat-launched multi-stage pilot must additionally prove deployment and original-chat delivery before release is called verified.

## Game-specialist intake

New chat-native game builds use `create_game_work_project`, which atomically preserves the original request identity and binds a versioned game specialist as the implementation worker. The specialist is pinned by immutable registry identity, definition version and configuration digest; duplicate display names are ignored, and later edits block new registrations. The lead still owns architecture/specification and delivery, research remains independently reviewed, and GitHub runs independent tests and code review. The Executive registry and Executive delegation paths are unchanged.

A game specification adds `game: {enginePath,rules,acceptance}` using the versioned game-rule framework. Rules record edition, original versus reproduction, primary/user sources, approved interpretations, unresolved decisions, invariants and initial state. Blocking unknowns prevent coding. Every approved rule needs scenario coverage, with both model and browser scenarios. The final browser contract must exactly execute the registered browser scenarios; it cannot be replaced by a loading-page check. The complete specification, including these rules and expected states, appears in the existing scope proposal and its immutable approval digest.

Registration is automatic through the saved project, scope and server-authored issue context. Chat projects use the existing native test/review/repair workflow and parent project repair budgets; no hand-written `config/game-projects` entry or owner PR comment is needed. The separate `game-review-repair` listener continues to handle later external Codex findings for its explicitly registered standalone games. These are separate repair entry points, not two listeners coding on the same chat milestone.

For the final increment, preserved trusted tools run the registered model scenarios against the actual pure engine export `transition(state,action)`. The engine is a self-contained `.ts` or `.mjs` module; UI, persistence and other application behavior remain separate. Candidate code runs without host credentials/network in the existing filesystem namespace and a restricted VM. Expected model states stay in the trusted controller; only state and action enter the engine process. Wrong states, mutation, crashes and missing exports fail verification. The raw `project-game-model.json` receipt binds the actual checkout SHA and is retained with browser artifacts and test logs. Earlier increments can retain their own partial browser contracts; final model and full browser checks are mandatory before delivery.

Existing deployment-bound Preview acceptance, whole-project assessment and idempotent original-chat delivery remain authoritative. A model pass or a local browser pass cannot complete a game project. Infrastructure failure must preserve the saved source for verification-only recovery; it is not permission to recode a validated game. Production publication remains a separate release action.
