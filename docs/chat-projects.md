# Chat-native projects

Katie can start a persistent software project from an explicit conversational request (including a same-chat “build that” referring to a saved user request). Ordinary questions and managed-agent/attachment conversations retain their existing paths. No agent dashboard is required. Project creation uses the durable chat request identity, validates the owning actor/chat and freezes the original user objective.

The scheduled mission dispatcher advances reviewed research, a structured specification, scoped approval, successive coding increments, preview delivery and a fresh whole-project assessment. Original objectives and user clarifications remain stored; each approved specification contains requirements, narrow allowed paths, phase-specific browser contracts, a complete final browser contract and finite ceilings. The last milestone must run the complete final contract. Phase success is never equivalent to whole-project success.

Coding requires an explicit connected target repository with the existing owner-only main-branch development workflow and private Preview deployment integration. Katie can ask for the repository in chat. The approved scope is presented concretely in that conversation, including all browser scenarios, allowed paths, source commit, deadline and budgets. One scope approval permits successive isolated draft jobs and bounded repairs within that scope. New services, credentials, dependency/deployment configuration, purchases, production publication and merging are not implicitly permitted. Targets must also be explicitly enabled in server-only PROJECT_PREVIEW_REPOSITORIES after their Preview environment is stripped of provider/GitHub/storage credentials and implicit cloud identity. Production and Development credential targets are preserved. Protected targets use an owner-configured production-only PROJECT_PREVIEW_BYPASS_SECRET and an anchored PROJECT_PREVIEW_HOST_PATTERN. Only Vercel’s edge receives that secret with manual redirect handling; the browser receives a short-lived HttpOnly cookie restricted to the exact deployment URL. No bypass secret is injected into Preview builds, application requests, logs or model evidence. Deployment protection stays enabled. Missing integrations remain blockers rather than fabricated delivery. This release does not provision a new repository or service automatically and does not claim to have recreated Fortress America.

Each coding job starts from the previous immutable READY tested/reviewed commit on a new isolated branch. Server-owned project context is derived from the approved DB record and appended outside model prose. Ordinary inputs cannot inject a project marker. The native workflow preserves the original task and trusted browser tools before switching to the prior project commit. Independent tests, code review and bounded native repair remain unchanged. Actual built Next application checks run in a separate Linux user/network/PID namespace, with placeholder credentials and no route to production networks. Acceptance helpers fail closed without namespace support. Candidate CI and the application run inside separate bubblewrap filesystem/PID/user boundaries: preserved contracts, tools, reports and parent processes are not mounted; baseline dependencies are read-only. Install hooks are disabled and dependency manifests must match the previous verified commit. Before either publishing push, a trusted scope guard rejects the full cumulative staged diff outside approved paths, protected configuration, symlinks or submodules. The candidate cannot replace the preserved contract/tools. Project receipts require the exact approved scenario names/digest and matching test/review/browser/head SHA. Repaired runs require repaired browser evidence.

Parent projects require a successful same-head Preview deployment obtained from GitHub deployment/status records, never from a model-supplied URL. A separate bounded browser_check phase then executes the exact final contract against that actual deployed URL. Authentication/401 failures block for connection repair; failed gameplay permits bounded implementation repair. The private browser receipt binds the deployment ID, status ID, SHA, contract digest, URL and scenarios. No deployed browser pass means no completion. A new deployment after assessment requires a fresh deployed check and assessment. The same preserved browser engine runs both local and deployed checks. The final independent mission assesses the entire original request against requirements and actual integrated evidence, and then returns the result to the original chat. Progress/final messages are persisted with stable IDs and chat polling only reads them; closing every browser does not stop the work.

Project limits are 8 native coding jobs, 12 milestone missions, 600,000 aggregate project-model tokens and 72 hours. Existing individual mission defaults remain unchanged. Native GitHub coding model usage is additional, explicitly disclosed in the scope approval, and bounded separately by the existing job time/repair limits. This is not a dollar spending cap. All reservations, including uncertain calls and failed/superseded missions, remain charged. Parent and child mutations use the same advisory lock to prevent oversubscription and lock inversion. Current agent permission/capacity checks remain authoritative. Pause/stop invalidates leases; accepted external work may finish, but late results cannot advance a paused project. Resume preserves remaining budgets and refuses an expired/blocked child rather than silently recreating its allowance.

Tables and RPCs are private, RLS enabled, SECURITY INVOKER with fixed search paths, and executable only by service_role. No browser receives a provider or database secret. Scope proposals are published in the same transaction as their digest. Digest-free approval requires the latest assistant proposal to carry the current full digest. Mid-project clarifications stop the superseded milestone and return to research/specification and fresh approval while preserving prior code and charges. Dispatch admission atomically checks parent scope/status/deadline and current assignment lease. Scope approvals are immutable digests; project controller outcomes and child creation are fenced and transactional. Message delivery is idempotent. Background controller failures block after three attempts.

## Validation

- projects-runtime: conservative natural intent, saved user-reference launch, request identity, scope-bound controls, cumulative two-stage coordinator, no completion without preview/final assessment, failed-browser rejection.
- projects-sql: real PostgreSQL project identity, actor/chat association, scope approval, child/lease fencing, pause/resume, immutable lineage, private privileges and concurrent aggregate reservation races.
- project-context / project-browser-check: strict marker/hash/parser bounds and real DOM interactions, deliberately wrong assertions, browser redirect confinement and server-side network isolation.
- autonomous-repair-handoff: actual workflow Bash, cumulative Git base, original trusted tools, missing/failed/wrong-head/partial/repaired browser receipt gates.
- Existing mission, managed-agent, chat, review, full CI build and smoke tests remain required.

Local runtimes without Linux user namespaces cannot execute the isolated acceptance integration. That is a failed local verification, not a reason to disable the boundary; complete CI runs it on the Linux runner. A live chat-launched multi-stage pilot must additionally prove deployment and original-chat delivery before release is called verified.
