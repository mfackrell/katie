# Project Director — Milestone 1

This additive slice gives each project one persistent accountable director and a
recursive management organization. It does not qualify the complete autonomous
software-development platform or authorize a production release.

## Ownership and execution

`work_projects` inserts create exactly one director with a separate managed-agent
identity. A unique partial index prevents duplicates. Historical projects receive
ownership metadata with `organization_version=0`; their state, team, missions,
spending and Task 4A authority are not activated or replaced. New projects use
version 1. Management identities are permanently recorded: replacing a leader
cannot turn its former identity into an execution worker.

The existing project controller schedules management sessions through existing
mission leases. Management dispatch accepts only bounded JSON decisions with no
technical tools. Database functions derive the principal from the live assignment
and lease. Assignment, agent-task, configuration and spending guards enforce the
same separation below the prompt. Workers retain existing mission/model or native
development execution. There is no new provider transport or alternative ledger.

Executive routing intersects live provider discovery with fresh verified registry
capability and pricing. Only available OpenAI/Anthropic models with verified high
reasoning capability are eligible. No fallback identifier is guessed. Atomic
financial admission remains mandatory; missing eligibility or authority fails
closed. Qualification uses deterministic providers, without real inference.

## Purpose, organization and authority

The director records purpose, direction, measurable outcomes and milestones bound
to the original owner objective. Its plan identifies the required organizational
areas; the controller waits until those chosen areas exist. The strategy and
accepted component evidence feed the existing technical lifecycle. Every manager
can plan and commission subordinate managers and workers recursively.

There is no fixed director count or organizational depth. Each appointment needs
positive inherited resources, contained tools and paths, a bounded deadline, and
a durable contract covering purpose, objectives, deliverables, acceptance,
interfaces and reporting. Sibling allocations plus the manager's own encumbrance
must fit the parent. Calls check every ancestor token allowance and the combined
project monetary ceiling. Existing mission-session limits bound operation rather
than organizational shape; new projects default to 64 sessions and historical
limits stay unchanged. Sixteen commands per decision bounds individual messages.

The authenticated owner grants one objective-bound original envelope through
`POST /api/projects/organization`: `projectId`, SHA-256 of objective plus
clarifications, `ceilingMicrousd`, `perCallMicrousd`, and explicit
`autonomousExecution: true`. This is original project authority, not a routine
approval per appointment or coding task. Publication remains separately governed.
An owner-facing intake approval interface remains subsequent work.

Managed coding tasks derive their native proposal and approval from that original
envelope, a live appointed-worker lease, current scope, dependencies, and remaining
ancestor/project resources. Existing native preparation, protected reserves,
dispatch claims, gateway admission and settlement remain authoritative. Two
successive coding tasks are tested under one envelope with no new owner consent.
The currently installed native adapter supports `mfackrell/katie`; unsupported
repositories fail closed rather than falling back to unmetered execution.

Scope approval creates a versioned root grant and invalidates stale acceptance.
Managers propagate only current approved paths. Dependency edges and inherited
completion dependencies must remain acyclic. Routine worker failures wake the
immediate manager; bounded repair and evidence-based resolution stay local.
Material exceptions move one reporting level at a time. Routine exceptions cannot
reach the owner. Failed management sessions receive two attempts before escalating
to their superior. Restart never recreates authority or erases consumed claims.

A superior can reject incomplete results, replace a subordinate leader, or move a
direct child under a sibling manager within the recipient's authority and remaining
resources. Contracts, descendants, decisions and spending remain durable. Transfers
invalidate affected acceptance and reject reporting/dependency cycles. Former
leaders remain structurally barred from execution.

## Acceptance and closure

Managers evaluate every delegated acceptance criterion against completed technical
assignment evidence from the child's subtree. Empty checks, forged assignment IDs,
and management activity reports cannot establish component acceptance. The superior
accepts or rejects the component against its original contract. Completion flows
upward; component acceptance alone cannot close the project.

Independent QA cannot inherit development authority. Project closure requires a
current assessment reviewer in the QA subtree, distinct from the author, with the
actual QA assignment accepted against the final head and scope. Only a live
Project Director session can write the closure authorization. Missing components,
open exceptions, failed original-requirement checks, absent exposure records or
unsettled calls block it. Existing source-bound final completion, Preview and
browser gates still run afterward; the director receipt cannot bypass them.

Financial receipts separate actual recorded tokens, conservative verified-price
mission cost bounds, and canonical native exposure. They are not supplier invoice
reconciliation. Unknown liabilities block closure. Actual overruns are recorded
and block further execution rather than rejecting accounting receipts.

## Deterministic qualification

* `project-organization-postgres.test.mjs`: actual PostgreSQL transactions exercise
  unique ownership, recursive authority, concurrent lease replay, unauthorized
  role changes, reporting cycles, forged evidence, spending limits, local repair,
  escalation, reconnect durability, bottom-up component certification, failed QA
  and director-only closure authorization. Technical outputs are deterministic
  fixtures, not a claim of an inferred application built end to end.
* `assert-dynamic-project-management.mjs`: projects whose plans require 2 and 24
  directorates, a ten-level hierarchy, unaffordable growth, rejection, leadership
  replacement, bounded transfers and inherited dependency-cycle rejection.
* `project-organization-runtime.test.mjs`: verified executive eligibility,
  management-only dispatch, separate worker completion, derived native authority
  and authenticated explicit original consent.
* `project-organization-integration.test.mjs`: installs the migration after the
  actual ordinary-authority/native stack; compares historical project, mission
  and financial snapshots; exercises canonical gateway admission and settlement.
  `assert-project-native-delegation.mjs` additionally covers two version 1 native
  tasks, concurrent idempotent preparation, original-envelope authority, preserved
  protected grants and real ledger settlement with synthetic provider usage.
* Existing project/mission/dispatch regressions, typecheck, build, Full CI and an
  independent security review remain required for candidate qualification.
