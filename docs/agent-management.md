# Persistent agent management

This increment adds `/agents`, linked from the existing sidebar. Managed agents have their own existing `actors` identity; ordinary actors are neither imported nor converted. Definitions, original task inputs, trusted configuration snapshots, current continuation turns, chat identities, request IDs and development receipts are persisted in Supabase. Archiving preserves the actor, chats, task records and memory, rejects new tasks/starts/continuations, and allows already admitted work to finish. Managed identities and task histories cannot be deleted through ordinary actor/chat deletion; database foreign keys also protect them.

## Installation and ownership

The coordinator must review and apply `supabase/migrations/20261016211426_agent_management.sql` through the existing migration runner, in normal filename order, before serving this code. It depends on existing UUID actors/chats, `repo_sync_runs`, and the existing chat request/progress migrations. No existing migration, workflow, production data or live schema was modified by the implementation job. The migration adds three service-only tables, validating invoker functions, and identity indexes/foreign keys. All three tables enable RLS and revoke PUBLIC/anon/authenticated access. Every new function fixes `search_path=public`, uses SECURITY INVOKER, revokes PUBLIC/anon/authenticated execution, and grants service_role only. Configuration checks reject unknown/invalid shapes and unsupported capabilities in SQL as well as TypeScript.

The existing private single-owner Vercel Authentication ALL deployment remains the access boundary. An actor ID is an isolated workspace identity, not a new login. No public authentication route, secrets UI, new dependency, scheduler, provider framework or coding orchestrator was added. Existing Supabase service-role and `GITHUB_TOKEN`, `GITHUB_PAT`, `GH_TOKEN` server credential conventions are reused.

## General tasks and controls

Save a definition with its name, instructions/responsibilities, live-research permission, development-submission permission, independent-review preference, maximum active tasks (1–4), and maximum characters per user turn (100–16000). Instructions are bounded to 12000 characters and names to 80. New UI definitions default to **Always** independent review; **Adaptive** reuses the existing actor preference. Mandatory runtime review checks and saved-draft verification continue to run through the existing engine. There is no permission to skip an otherwise-required review to meet a budget.

Save a task, inspect its saved configuration, then start it. Creation allocates its chat and copies the definition inside one SQL transaction. Starts and continuations lock the definition and task and atomically admit against the smaller of the saved and current active-task limits. Running, pending-review, dispatching and submitted workflow tasks consume admission. Drafts do not. Terminal tasks release admission after their durable status is refreshed. Definitions can change without altering an admitted task's instructions, review preference, permissions or input limit. The original task input is retained separately from later continuation turns.

General execution calls the existing `/api/chat` route and its existing routing, memory, collaboration, required-review, persistence and request-recovery mechanisms. It does not create another provider/review pipeline. A durable execution claim occurs before attachment selection or provider work; concurrent/repeated starts cannot run the same turn twice. Managed requests must match the admitted actor, chat, request ID and saved turn. Browser-supplied model overrides, snapshots, unknown execution fields and repositories are rejected. Configuration/lookup errors fail closed. Ordinary actors retain their normal routing and limits.

The **Live web research** permission is enforced at the actual browser collector, research helper and Grok web-tool adapter with request-scoped async context, including independent review/escalation calls. Scope isolation is covered by concurrent mocked execution tests. Disabling research can leave a task pending when its requested evidence/review cannot be obtained; a model prompt is not the enforcement boundary.

**Attachment/media access and connected-repository reads are unavailable for managed general tasks in this increment.** Attachment permission must be false in both the SQL and API schemas. New attachment/image references are denied before hydration/provider work, and the separate durable video-handoff registration API rejects managed actors. Saved-source metadata is checked, and managed saved-video/evidence entry points return without inspecting source bodies. Browser-provided `activeRepoId` and enabled repository injection are rejected; the route disables repository injection for every managed task. Ordinary actor attachment ownership/cache rules and repository behavior remain in place. Code analysis/drafting does not execute generated code. No general model tool receives send, write, merge, deploy or production-resource permissions.

The input and active-task bounds are enforceable limits. Existing runtime request duration, execution deadlines and bounded collaboration/delegation settings apply; the UI does not advertise a hard dollar/token budget or guaranteed completion time. There is no new background task executor. Work runs inside the existing request lifecycle. Browser loss does not establish success: use **Refresh status**, **Resume saved request**, or reload the saved task URL. A repeated request observes the saved claim/status rather than launching replacement provider work. An interrupted turn is never automatically replayed. Status refresh locks the saved task and its matching durable request, validates their associations, and marks an abandoned running turn failed after 20 minutes from admission (before a claim) or the fixed execution-claim timestamp. This exceeds the existing route’s 800-second maximum request lifetime; status reads do not extend the claim lifetime. Recovery handles both missing request records and interrupted processing records. Terminal request records remain authoritative. The owner can then explicitly continue the same chat with a new request ID and the original configuration snapshot. The old turn cannot be claimed again. Recovery does not claim to cancel a running model or to complete its review. No cancellation control is offered. Management lists are bounded to the latest 200 definitions and 100 tasks; older task/chat deep links remain inspectable, but this increment does not add list pagination.

Status refresh reads the existing durable chat request, independent-review audit and source-linked question ledger. HTTP 200, stream completion and nonempty text alone are insufficient. Unavailable/incomplete review or unanswered questions stay pending; failures show their stored error. The management screen exposes actual output, review audit and progress details. Continue a pending/failed/completed task in the same chat using its continuation form; it receives a new durable request ID while retaining its saved configuration and original input. **Open existing workspace** opens the original actor/chat history, whose composer links back to the managed task instead of sending unbound requests. Chat status validates record/chat/actor and managed-task identity; composite database foreign keys prevent rebinding a managed chat to another actor.

## Approved development handoff

Development tasks require the saved development permission and an existing connected repository. The server saves its full repository name alongside the connected-repository ID and refuses dispatch if that binding changes after approval. Saving alone performs no external write. **Approve exact saved task and submit to GitHub** approves the stored task ID, original input, definition version, instructions and repository; browser JSON cannot replace that snapshot during approval.

Before issue creation the server checks GitHub's authenticated user and repository owner. Both must be human `User` identities and the authenticated login must equal the repository owner's login. App/bot tokens, collaborators, organization members and unavailable credentials produce a persisted **blocked integration** explanation, with no claim that coding started. Configuration may still be saved and tested without usable owner credentials. The existing autonomous-development workflow must also be present and active; missing/disabled workflow integration blocks submission before an issue is created. No owner-only workflow gate is weakened and no keys are requested from the user.

A single durable dispatch claim precedes the external write. Issue creation uses structured Octokit arguments, an `[agent]` title, and a task UUID marker in its body. Success saves the issue link and number. A network error after possible acceptance stays **dispatching/uncertain** and never blindly retries creation. Explicit refresh searches the latest 100 owner-authored issues for the exact marker and reconciles an accepted issue. If none is found, uncertainty remains visible; this bounded search cannot prove absence and does not authorize another write.

Manual refresh has a bounded 60-second reconciliation window within a 120-second API request limit and checks at most 20 runs of the existing `autonomous-development.yml` workflow on the connected repository's `main` branch, at most 20 artifacts per completed run, and its `agent-completion` artifact. It requires matching repository/issue/run IDs in `agent-result.json`. Only same-repository main-branch issue/workflow_dispatch runs qualify. The ZIP/JSON parser is bounded, extracts only the fixed receipt filename in memory, and never runs archive content. GitHub response reads are bounded to 8 MiB with the existing request timeout; receipt artifacts are limited to 1 MiB and receipt JSON to 64 KiB.

READY additionally requires workflow success, the exact READY outcome, a same-repository PR URL, successful build, and the existing independent-test/review or bounded-repair/final-review success combination. Failed checks remain BLOCKED even if a malformed receipt says READY. The issue, run, PR, receipt and check results are persisted and visible. READY means **draft ready for owner approval**, never deployed or merged. This is a bounded view of verified receipts, not endless polling or a promise that every old run remains discoverable. Runs without a matching receipt are not inferred successful. Existing workflow artifacts/comments remain the diagnostic source for full test/review findings. There is no retry/reopen/cancel/merge/deploy action here.

## Continuation retry identity

The continuation API requires a client-generated turn UUID (`turnId`) and the current base request ID (`expectedRequestId`). Before sending, the UI saves this identity and the submitted text locally so a reload after response loss can retry the same turn. SQL serializes admission and stores an immutable receipt. Retrying a key returns its original receipt during execution, after completion and after later turns; changing its input or base is rejected. A different key from a stale base is also rejected. The API returns the receipt separately from current task state, and the UI never executes a later current request on an older receipt. **Retry saved continuation** resolves uncertain acceptance; it does not authorize automatic replay. Receipt tables explicitly revoke inherited Supabase grants before granting service-role SELECT/INSERT only.
