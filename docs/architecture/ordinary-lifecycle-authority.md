# Ordinary Developer first-shortage authority

Implementation design; not a delivery or qualification claim.

The existing project scope approval does not establish a native execution grant,
native-call ceiling, or monetary ceiling. Those values must be explicitly displayed
and approved by the authenticated owner. Existing scope approval, actor/chat IDs,
and a forecast alone never authorize native execution.

## Shared contracts

- Keep `work_projects`, `project_runs.binding`, original assignments, and frozen
  acceptance criteria authoritative for scope and task identity.
- Keep canonical provider operations in the existing budget-call ledger and their
  linked `mission_calls`; retain conservative dollar exposure and receipt settlement.
- Extend existing spending approvals and execution grants with an explicit ordinary
  project binding. Ordinary rows have no benchmark experiment, trial, qualification,
  or continuation. Database XOR checks prevent mixed authority.
- Reuse immutable lifecycle proposals, authenticated owner route/component, and
  decision transactions. A first amendment points to the original ordinary approval;
  it does not require a prior amendment. A unique parent prevents sibling authority.
- Reuse signed dispatch, native host, provider gateway, and Task 1 restoration. The
  signed authority kind selects validation; it cannot bypass either kind's checks.

## Enrollment and historical evidence

Original ordinary execution authority requires authenticated owner approval, exact
scope and model binding, explicit calls/tokens/dollars/reserves/window, and verified
ownership. A previously approved coding scope cannot silently become native spending
consent. Existing projects with unaccounted external native work must fail closed;
missing receipts do not establish zero spending. No production grants or enrollment
records are created by migration or qualification.

## Approval and admission

Lock the current approval, account, task, and project under the existing mission
transaction lock. Revalidate the immutable displayed proposal and checkpoint, then
append one decision and one child approval. Preserve the original account and every
historical call. Native, completion, routing, and assessment reservations share the
same cumulative capacity. Protected stage reserves remain inaccessible to repair.

Approval, dispatch claim, and grant issuance remain distinct, single-use boundaries.
Unknown charges prevent duplicate paid work. Expired/revoked/missing grants remain
denied until a valid explicit renewal has committed. A provider receipt can settle
only its canonical existing reservation; it cannot increase authority.

## Review requirements

Audit every legacy function affected by ordinary rows: issue, reserve, live, stop,
claim, settlement, effective limits, and projection triggers. Prove cross-mode denial
with actual PostgreSQL transactions, including three reservations for two slots and
concurrent first-amendment decisions. Preserve v5/v6/v7 benchmark regressions.

## Task accounts and capability limits

Each original development task has one ordinary account bound to its project and
assignment. Subsequent amendments retain that account; a later project milestone
requires its own original authenticated authority. Accounts do not transfer limits
or erase earlier spending. Existing project-wide token admission aggregates every
mission under the mission-state lock. Unsettled prior project-account calls prevent
new enrollment. The final assessment binds the latest development task's account.

The supported trusted native host remains `mfackrell/katie` with its approved pinned
native model. Other repositories keep their existing dispatch contract. Ordinary
calculation tools are retained. Separately billed research tools fail explicitly
until their monetary exposure can be authenticated; the benchmark-only frozen
no-tools restriction is not silently applied to ordinary tasks.

Original proposals use the existing development mission's token/call allocation,
with explicit protected completion and assessment reserves. Their proposed monetary
maximum is the authorized token allocation times the greater verified input/output
price, rounded upward in microUSD; this is a maximum, not a spending estimate.
Original project token and expiration controls still apply. No record is enrolled
by migration, and proposals create no authority before authenticated commitment.
