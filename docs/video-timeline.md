# Sampled visual video event timelines

This increment adds opt-in measured visual observations to the actual chat route. Ordinary Gemini/RunPod/Grok video description, ten-frame fallback, original retained recordings and prior complete descriptions keep their existing paths. There is no deployment, auth change, cron, new endpoint, model dependency, historical backfill, audio transcription, troubleshooting work or live replay acceptance test.

## Invocation and coverage

Mark can attach one recording and say **“Build a timestamped timeline.”** For a saved recording, name it or say **“Build a timestamped timeline of my saved video.”** A unique current recording is reused without asking for internal IDs. Fresh video uploads take priority. Multiple candidates, including identical filenames, prompt source clarification rather than selection by filename alone. A project/business timeline does not enable video analysis.

Follow-ups include:

- “When did the error first appear?” searches stored observations, ordered by earliest measured positive sample. This is read-only: if evidence is missing, request a timestamped timeline or a numeric inspection interval.
- “What happened in the last30seconds?” uses the trusted measured duration and allocates samples inside that interval.
- “What happened between00:20 and00:45?” accepts seconds, MM:SS or HH:MM:SS independently of upload-date search. Invalid/reversed/out-of-source intervals clarify rather than broaden the scope.
- “Continue the timestamped timeline” advances past contiguous completed windows, up to the whole-pass cap below. Failed/partial windows remain visible; they are not automatically analyzed again.
- Repeat a numeric interval with “page 2”, “page 3”, etc. to retrieve subsequent chronological observation pages. Pages contain 100 observations, with a 101st-row continuation sentinel. “First” always searches from offset zero and returns the earliest matching stored observation, rather than a text-ranked excerpt.

Every answer receives attachment identity, retained-content SHA-256, analysis version, model provenance, requested interval, actual sampled positions, processing status and unknown-gap caveats. Event ranges are computed from referenced decoded frame IDs. Numeric search requires an actual positive sample within the requested range; a span across an unsampled gap does not match that gap. SQL applies English full-text search and chronological ordering across stored windows before pagination.

A window marked `complete` means its bounded sample batch was processed, **not** that every frame or event was analyzed. Fewer than ten distinct decoded samples, or a provider-declared partial result, publishes `partial`. All unsampled positions remain unknown. “First observed at” does not prove event onset, continuity, duration or absence of brief events. Sound is never evidence in this feature.

## Operational bounds and durability

One explicit turn executes at most **one new window, 30 seconds, ten JPEG evidence frames and one Grok inference attempt**. Whole-pass continuation covers at most the first **120 seconds / four chronological 30-second windows**. Longer recordings remain explicitly partial; users can request later numeric intervals. A requested interval longer than 30 seconds processes its first 30 seconds; the rest remains unprocessed and must be requested separately. No background timer, automatic continuation or recurring worker is introduced.

Source bytes are capped at 200 MiB. Probing times out after eight seconds. Each decode command has a twelve-second cap and the window loop has a sixty-second deadline. Each returned JPEG is at most 350,000 bytes, with strict-path FFmpeg scaling bounded to 960 × 960. The ending sample scans at most the final two seconds into one overwritten JPEG, capped at 1,000 decoded frames; reaching that cap discards the ending sample conservatively. The opt-in Grok observation request has a 180-second HTTP timeout, a 6,000-token output cap and zero SDK inference retries; normal chat requests retain their existing options. The SQL lease is 120 seconds, informational only: expiry never authorizes a second provider attempt.

The stable database identity is live source chat + attachment UUID + retained SHA-256 + `visual-sampled-v1` + requested numeric window, scoped to actor. The actor's source and target chats are locked and checked in every RPC. A unique atomic claim creates a durable receipt **before** inference. Concurrent requests cannot multiply inference for the same window. Attempts are capped at one. Processing, partial, complete and failed results are durable and readable; pending is reserved by the schema. There is deliberately no reclaim/retry after lease expiry or an ambiguous provider outcome. This provides no exactly-once guarantee for external inference. A lost response can leave a processing/failed receipt even when the provider accepted the request.

Raw bounded reports (up to 24,000 characters) and frame evidence are retained even when returned JSON is invalid. Reports beyond that bound retain only the bounded prefix and a failed status. Unknown/foreign frame IDs, extra authoritative time/source fields, empty/refusal reports and duplicate evidence identities are rejected. Server frame IDs bind the source fingerprint, actual PTS and image digest. Completed/partial event descriptions are transactionally indexed through existing media-memory mechanics; the original structured report and all previous reports remain separate.

Tables are service-role-only with RLS, explicit PUBLIC/anon/authenticated revokes, SECURITY INVOKER RPCs, fixed search paths and source-chat cascading deletion. Live ownership locks prevent late completion after source deletion from resurrecting SQL evidence. Cache recall hashes the retained original again to detect replacement at the same object path; it makes **zero decoder or media-provider calls**. This has a bounded private-storage download/hash cost, up to 200 MiB per recall. Legacy sources are fingerprinted from actual retained bytes without rewriting their canonical metadata. A mismatched previously recorded fingerprint hides old cache evidence and requires a new retained source.

Timeline context is supplied to normal synthesis and independent assessment. Saved-draft/clarification review restores cached context only, preserving the original task without using the prior candidate as measured evidence. Source clarification and decoder/provider failures do not activate the ordinary whole-video fallback.

## Decoder semantics and explicit limits

Only zero-origin recordings with a trustworthy finite duration (at most 24 hours) qualify. Unknown-duration and nonzero-origin containers return an explicit unsupported limitation; no tail endpoint is guessed. VFR uses decoded `showinfo` PTS, not seek labels. The first snapshot uses the first emitted frame's PTS: FFmpeg can log a look-ahead frame after a one-image output. The ending scan uses its last emitted PTS. Repeated PTS are deduplicated; static images at different PTS remain distinct source frames. Temporary directories are removed in `finally` on success and failure.

An exhaustive whole-recording pass beyond 120 seconds, automatic recovery of ambiguous calls, provider idempotency, deeper analysis versions, audio, and autonomous scheduling are deferred. Metadata/status reads return at most 100 windows; the context flags possible truncation. Event search orders across all matching windows in SQL and is separately paginated, so this window-metadata bound does not turn first occurrence into a text-ranked guess. Broad first-occurrence questions only establish the earliest **stored** matching sample and always retain unprocessed-window/gap caveats.
