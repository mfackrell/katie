## Storage and isolation

`20261014220000_media_memory.sql` is additive. Supabase CLI was not installed (`command -v supabase` returned no executable), so its migration generator could not be used. The migration uses PostgreSQL generated tsvector/GIN, invoker functions with fixed search paths, explicit PUBLIC/anon/authenticated revokes, service-role grants, and RLS without client policies. It requires the existing actors/chats/video_analysis_jobs tables and normal Supabase roles. Apply database first through the coordinator's normal migration process; application failures during rollout defer indexing and describe search as unavailable.

The index distinguishes discovery, extracted text, model analysis, and measured timing. Text uses 4,000-character overlapping windows at stable 3,600-character offsets, including every available character. Extracted chunks retain their own part/version identity even when extractedText also exists. Video versions retain job identity, full original model name, and a content checksum; Qwen and Grok remain separate reports. Canonical private JSON and operational reports retain the original text. Each RPC limits work and arguments; a single evidence part above 10 million characters is rejected, retained canonically, and remains pending rather than silently truncated.

Source-chat FKs cascade deletion independently of Storage cleanup. Writes lock and verify the live source owner; reads validate the current chat/actor and join the live source owner. Actor UUID selects scope and is not authentication. Only the server/service role may invoke these functions. No public search route, client grants, parent/subactor expansion, or filename/provider-ID ownership inference was added.

## Ingestion and recovery

Trusted upload persistence indexes existing saved descriptions and exact extracted text. HMAC-bearing references are reread privately; client decoderTiming is discarded. Timing comes from the existing exact-frame registry and shared source/timing formatter. No new descriptions or media analysis are generated by indexing or retrieval.

Future eligible canonical JSON includes a durable pending bit and descriptor, with a private secondary pending marker. Each chat request retries at most three pending uploads and checks one canonical record using a durable rotating actor cursor, including recovery when the secondary marker was lost. Failed entries rotate by update time. Owner checks precede private canonical reads; SQL enforces ownership again at commit. Uploads without trusted persistence provenance and historical records without the explicit pending bit are not opportunistically backfilled.

A database trigger indexes usable completed Qwen/Grok reports without changing operational rows. Bounded reconciliation handles at most three registered live video jobs, including already-delivered jobs and late completion; it runs before the delivered early return and from chat construction. Existing refusal prefixes are excluded. Only an exact source path linked to already registered evidence and a live matching actor qualifies. Null-chat/orphan records remain untouched. Missing infrastructure never resubmits a provider job. Deferred work emits fixed diagnostic labels without private text or URLs.

## Conversation behavior

Historical locator/recall retrieval precedes original restoration and searches the eligible SQL corpus before the existing 40-summary limit. Matching, empty, unavailable, and clarification outcomes all suppress the media selector/restorer. New uploads and explicit inspection requests retain source routing. Recent anchored current-chat video follow-ups retain their existing path; historical/date references use the new index.

Query preparation removes conversational boilerplate and searches quoted terms with OR ranking. Supported dates are UTC yesterday, previous Monday-through-Sunday calendar week, and inclusive `YYYY-MM-DD to YYYY-MM-DD` upload ranges. Unsupported recognized relative dates ask for an explicit range. Video/image/PDF/spreadsheet/document constraints are applied in SQL. This is lexical search, not semantic similarity; descriptions with no shared indexed vocabulary may need clarification.

Results contain bounded excerpts, source chat/attachment identity, filename, evidence kind/version, character offsets, and honest coverage. Multiple identities generate a grounded clarification. The context treats all source text as untrusted, separates requests/reports, forbids fresh-inspection claims and inherited Grok/Qwen agreement claims, and checks original availability using at most four owner-checked metadata-only HEAD requests, without opening media. Missing originals are labeled unavailable; errors or excess candidates are labeled unknown. `read_media_evidence` supports additional versioned text by source/offset; the conversational `saved-evidence:{...}` reference invokes it without opening media. Drafting and independent assessment receive evidence after original-task/clarification selection, without adding the candidate draft.
